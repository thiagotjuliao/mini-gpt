Q1fácil

Se y = f(x) e z = g(y), a regra da cadeia diz que dz/dx é igual a:

Resposta: B. A derivada flui de trás pra frente multiplicando as sensibilidades de cada etapa intermediária: o quanto z muda por x é (o quanto z muda por y) vezes (o quanto y muda por x). Isso generaliza pra cadeias arbitrariamente longas.
Q2fácil

No grafo de computação, o que exatamente previous (_prev) e _backward guardam num tensor de saída?

Resposta: C. Cada operação cria um tensor de saída que "lembra" de onde veio (previous) e sabe, via _backward, como usar a regra local daquela operação específica pra propagar gradiente pras entradas. Ligando essas referências entre tensores, formam o DAG.
Q3fácil

Por que o gradiente é acumulado (+= / accumulate) em vez de sobrescrito (=)?

Resposta: A. Se um tensor é reusado (ex.: a aparece duas vezes no grafo), cada caminho contribui uma parcela do gradiente total. Sobrescrever perderia a contribuição anterior — um bug silencioso, já que o código roda sem erro, só produz números errados.
Q4médio

Por que backward() precisa visitar os nós numa ordem específica (topológica reversa), em vez de qualquer ordem?

Resposta: A. Processar fora de ordem acumularia gradiente parcial num nó e propagaria valores incompletos adiante — não é uma questão de performance, é de corretude. A ordem certa garante que consumidores são processados antes de suas dependências.
Q5médio

No grafo "diamante" (um nó d alimenta dois caminhos, x e y, que só se reencontram depois, em loss), quando d pode ser processado no backward?

Resposta: B. Esse é o caso clássico que testa a ordenação topológica: mesmo d não sendo uma folha, ele só está "pronto" depois que todos os seus consumidores (x e y) já propagaram gradiente pra ele. Foi exatamente um bug real do projeto (documentado no HISTORY.md) quando o algoritmo esquecia de marcar nós intermediários compartilhados corretamente.
Q6médio

Pra que serve zeroGrad() e quando ele deve ser chamado?

Resposta: C. Como accumulate sempre soma (nunca sobrescreve), sem chamar zeroGrad() antes de um novo backward() o gradiente do passo de treino anterior ficaria misturado com o atual — corrompendo o treinamento silenciosamente.
Q7difícil

Mesmo grafo do HISTORY.md (c = a + b, d = c * a), mas agora com a = 3, b = 4. Depois de d.backward(), qual é a.grad?

Resposta: A — 10. Forward: c=3+4=7, d=c·a=7·3=21. Backward, semeando d.grad=1: contribuição direta do mul, a.grad += d.grad·c = 1·7 = 7; contribuição via add, primeiro c.grad += d.grad·a = 1·3 = 3, depois a.grad += c.grad·1 = 3. Total: a.grad = 7+3 = 10. Verificação simbólica: d=(a+b)·a=a²+ab, ∂d/∂a=2a+b=2·3+4=10 ✓.
Q8difícil

Rodando uma operação dentro de um bloco noGrad { ... }, o que acontece?

Resposta: B. Construir o grafo (previous/_backward) tem custo de memória e tempo que é puro desperdício em inferência (nunca vamos chamar backward()). noGrad desliga só a gravação do grafo — o valor calculado no forward continua correto, só não fica registrado como desfazer o cálculo.
Q9desafio

A ordenação topológica é construída via DFS que só adiciona um nó à lista de saída depois de visitar todos os seus predecessores, e depois a lista é invertida. Por que isso garante "consumidores antes de dependências"?

Resposta: A. O ponto-chave é o "depois de visitar todos os predecessores": isso força qualquer dependência (X) a já estar na lista antes do nó que depende dela (Y) ser adicionado. A lista pré-inversão está em ordem "dependências primeiro"; invertendo, vira "consumidores primeiro" — exatamente o que backward() precisa.
Q10desafio

Um tensor x é usado como entrada em 3 operações diferentes, cujos resultados eventualmente convergem (direta ou indiretamente) numa perda escalar L. Depois de L.backward(), quantas contribuições distintas x.grad deve ter acumulado?

Resposta: B. O exemplo do HISTORY.md/teoria usa 2 caminhos (a direto no mul e via add→c), mas o princípio — somar a contribuição de cada caminho que uma variável influencia a saída — generaliza pra qualquer número de usos. Não há limite de 2; são exatamente tantas contribuições quanto usos diretos de x como entrada de alguma operação no grafo.
