Q1fácil

Por que onehot(t) @ Table é matematicamente igual a pegar a linha t de Table direto?

Resposta: C. (onehot(t) @ Table)[j] = Σₖ onehot(t)[k]·Table[k,j] — só o termo k=t sobrevive (§1 do .md).
Q2fácil

Qual é a shape da tabela de Token Embedding?

Resposta: B. A opção D é a shape da tabela posicional, não a de token — as duas tabelas têm papéis diferentes (§2 e §4 do .md).
Q3fácil

Pra que serve o Positional Embedding, se o modelo já tem o Token Embedding?

Resposta: D. A atenção (Etapa 11) computa médias ponderadas entre posições, sem noção intrínseca de ordem (§4 do .md).
Q4médio

Usando Table de 09-embedding.md §1 e a sequência tokens=[1,0,1]: qual é tokenEmb?

Resposta: A. Cada posição da sequência vira a linha do token correspondente — a posição 0 usa token 1, a posição 1 usa token 0, a posição 2 usa token 1 de novo (§2 do .md).
Q5médio

Por que o gradiente do Token Embedding é chamado de "esparso"?

Resposta: C. dTable[t] = Σ_{i: tokenᵢ=t} dY[i] — soma sobre um conjunto vazio pra tokens ausentes, dando zero (§3 do .md).
Q6médio

Existe gradiente em relação ao próprio Array[Int] de tokens (os índices)?

Resposta: D. Fecha o ponto deixado em aberto em 07-tokenization.md §6 — o índice é só um endereço, não um valor diferenciável (§3 do .md).
Q7difícil

contextLength=4, seqLen=3. O que acontece com a linha 3 de PosTable nesse forward?

Resposta: B. PosTable tem contextLength linhas reservadas pro maior seqLen possível; sequências mais curtas simplesmente não alcançam as últimas linhas (§4 do .md).
Q8difícil

Batch de batchSize=2, mesma posição i=1 nas duas sequências, dY[0,1]=[2,0.5] e dY[1,1]=[1,2] (09-embedding.md §5). Qual é dPosTable[1]?

Resposta: C. Diferente do Token Embedding (que soma só as ocorrências daquele token), toda linha de PosTable usada soma sobre todo o batch, sempre (§5 do .md).
Q9desafio

Ao somar y = tokenEmb + posEmb, como o gradiente dY se divide entre os dois ramos no backward?

Resposta: A. É a mesma regra do + já provada na Etapa 3 — nenhuma matemática nova aparece aqui (§6 do .md).
Q10desafio

Batch de batchSize=2: tokens[0]=[1,0,1], tokens[1]=[1,2,0] (§6 do .md). O token 1 acumula gradiente de quantas posições, e espalhadas por quantas sequências diferentes?

Resposta: D. O scatter-add do Token Embedding soma sobre o batch inteiro achatado, não só dentro de uma sequência — dTable[1] = dY[0,0]+dY[0,2]+dY[1,0] (§6 do .md).
Q11desafio

Por que positional embeddings aprendidos (GPT) ficam limitados a contextLength, enquanto os sinusoidais (Transformer original) não têm esse limite?

Resposta: B. A troca é generalização (sinusoidal) por simplicidade de implementação (aprendido) — mesmo espírito da escolha de tokenização character-level (§7 do .md).
Q12desafio

Por que um lookup eficiente de verdade (O(1) por token, sem montar o one-hot) não pode ser implementado inteiramente dentro de gpt.nn.Embedding, do jeito que Linear (Etapa 8) foi implementado inteiramente dentro de gpt.nn?

Resposta: C. Diferente de Linear (pura composição de matmul+add já públicos), um lookup eficiente precisaria de um primitivo novo dentro de scalagrad.ops — onehot(t)@Table é a alternativa que funciona só com API já pública (§8 do .md).
