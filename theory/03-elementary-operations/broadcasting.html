§1 O problema

Duas operações elementares (+, *, ...) exigem, em princípio, que os dois tensores tenham exatamente o mesmo shape — a operação é posição-a-posição. Mas isso obrigaria a duplicar manualmente um vetor de viés toda vez que ele precisasse somar em cada linha de uma matriz. Broadcasting é a convenção que evita essa duplicação: um tensor menor é tratado como se estivesse repetido, sem nunca copiar dado de verdade.

Unbroadcast é o problema espelhado, no backward: se um tensor foi "esticado" no forward, o gradiente que volta está no formato esticado — precisa ser somado de volta pro formato original antes de acumular.

§2 Regra de compatibilidade

Os shapes se alinham pela direita. Se um deles tem menos dimensões, o que falta é preenchido com 1 à esquerda. Depois disso, cada par de dimensões precisa ser igual ou um dos dois ser 1 — nunca os dois diferentes e maiores que 1.

FIG. 1Alinhamento pela direita: s1=(3,) vira (1,3) por padding; comparado com s2=(2,3), a dimensão 1 estica pra 2, a dimensão 3 já bate.
No código Shape.broadcast(shape1, shape2) (core/Shape.scala) faz exatamente essa validação e devolve o shape resultante — usado tanto pelo forward (broadcastTo) quanto indiretamente pelo unbroadcast.

§3 Esticar sem copiar: a view de stride 0

Um Tensor não guarda só o array de dados — guarda também strides: quanto pular em data pra avançar cada dimensão em 1. O truque do broadcasting é simples: se uma dimensão tem stride 0, "andar" nela não muda a posição de memória lida — ou seja, qualquer índice naquela dimensão cai no mesmo lugar.

FIG. 2data = [10, 20, 30] tem só 3 elementos, mas a view lógica "parece" ter 6 (shape (2,3)). Com stride linha = 0, index(0,j) e index(1,j) caem na mesma posição de data — as duas linhas leem exatamente o mesmo array.

Isso quebra o invariante mais simples que valia até a Etapa 2 (data.length == shape.product), que só era verdade porque reshape/transpose nunca mudam a quantidade total de elementos. O invariante atual do Tensor é mais geral: o maior índice de memória alcançável por shape + strides precisa caber em data — Σᵢ (shape[i]-1)·strides[i] < data.length — o que aceita naturalmente strides 0.

§3.1 broadcastTo: os dois casos

Depois de alinhar os ranks (padding de 1 à esquerda quando os ranks diferem), toda dimensão que é 1 no shape original — seja ela nova (do padding) ou pré-existente — ganha tamanho do shape alvo e stride 0. As outras dimensões mantêm shape e stride como estavam.

FIG. 3Caso A: (1,3)→(2,3), sem mudança de rank. Caso B (abaixo, texto): (3,) primeiro vira (1,3) via padding (stride da dimensão nova já nasce 0), e então segue pro mesmo caso A — os dois casos convergem pro mesmo resultado final shape=(2,3) strides=(0,1).
Tensor.make([10,20,30], (1,3)).broadcastTo((2,3))
  → shape=(2,3)  strides=(0,1)          // caso A

Tensor.make([1,2,3], (3,)).broadcastTo((2,3))
  → pad rank: shape=(1,3) strides=(0,1)  // dimensão nova, stride já 0
  → shape=(2,3) strides=(0,1)            // caso A de novo

§4 Backward: por que reuso exige soma

Quando um tensor v é lido em mais de um lugar do grafo (aqui: em cada "cópia" broadcastada), a regra da cadeia multivariável diz que o gradiente de v é a soma das contribuições de cada uso — exatamente o mesmo princípio já usado quando um tensor é reaproveitado em operações normais (Etapa 2), só que aqui os "usos" são as posições broadcastadas.

FIG. 4v foi lido duas vezes (broadcastado em duas posições) — o gradiente que chega em v soma as duas setas, não fica só com a última.

§5 unbroadcast: desfazendo no gradiente

unbroadcast(grad, gradShape, targetShape) é o inverso de broadcastTo: recebe o gradiente no shape esticado (o da saída) e devolve um gradiente no shape original, menor — somando toda posição que, no forward, veio da mesma célula de memória.

Existem dois casos, e eles terminam de jeitos diferentes:

FIG. 5Esquerda: M(3,4)+v(4,) — coluna inteira soma numa posição de v.grad; a dimensão de linhas não existia em v, então some (squeeze). Direita: M(3,4)+b(3,1) — linha inteira soma numa posição de b.grad; a dimensão de colunas já existia em b com tamanho 1, então permanece (keepdim).
